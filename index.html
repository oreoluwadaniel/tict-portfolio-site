Project 1

Terminal Operations Command Dashboard

Power BIDAXPower Query

A three-page report for the terminal manager who starts every morning asking one thing: where are we losing time, and where are we losing money?

The problem

Ship waiting, gate queues and yard stays sit in separate files, so nobody sees the whole picture. Charges for containers that stay too long keep growing while the answer is still being put together.

What I built

  • Overview page with six headline cards, the TEU trend, a shipping line league table and the eight items most worth chasing
  • Vessel and Berth page showing berth timeline, waiting time by shipping line and the longest waits
  • Gate and Yard page with truck turnaround by lane, a busy-hours map, haulier comparison and yard block map
  • A hidden detail page for any single vessel call, compared with that line's average
  • A time window control (7 to 90 days or all) and filters for line, lane and haulier

What it shows

133vessel calls in the period
21,144containers handled
NGN 106.2mdemurrage building up on 607 boxes still in the yard
NGN 490.6mdemurrage collected in the last 30 days

Every figure was checked against a separate calculation done outside Power BI. Realised and building-up charges are always shown apart so they are never added together.

Project 2

IT Support and Equipment Reliability

Power BIPostgreSQLSQLDAX

A database layer and five-page report that shows where IT delays and machine breakdowns cost the terminal most, and which repeat support work to automate first.

The problem

IT and engineering managers need to know where to add support cover, which machines need a review, and which routine tickets are worth automating. The raw logs could not answer any of that.

What I built

  • PostgreSQL database with the ticket, breakdown and data-link logs, 23 built-in checks and a read-only login for reporting
  • Overview page, IT Support page, Equipment page, Automation page and a one-machine case file
  • Downtime counted without double counting events that overlap on one machine
  • Time saved estimates for routine ticket types, shown as hours per year

What it shows

89.0%of 1,800 tickets fixed within target, against a 90% goal
74.5%on-time rate for urgent (P2) tickets, the weakest group
32.0%night shift first replies that miss target, against 7.9% on days
55.9%of breakdown hours come from three fault types
723 hrsa year could be saved by automating five ticket types

358 breakdowns cost 6,288 hours of downtime. Average repair time is 16.3 hours and the fleet was available 97.95% of the time. 97.5% of 5,490 data transfers succeeded.

Project 3

Daily Operations Automation

Power AutomateExcelHTML email

Three Power Automate flows that run the terminal's morning routine so the report, the alert and the data check are done before the manager sits down.

The problem

Each morning someone opens several spreadsheets to see how yesterday went, which containers are costing money and whether the data is complete. That takes time and gets skipped on busy days.

What I built

  • 6:00 data check that confirms the day's data exists and raises a failure email with the failed step and a link to the run
  • 6:30 alert listing containers with the highest charges, sent once and marked so nothing is reported twice
  • 7:00 designed email report comparing yesterday with the previous 7-day average
  • Settings such as the report date, alert limit and recipient kept in a table, so changes need no flow edits
  • Every failure written to a run log with the error message

What it shows

3daily flows, each with its own run history
10 of 10recent alert runs succeeded
9 of 10recent report runs succeeded
14test cases written, including a forced failure

The screenshots are taken from Power Automate itself. Five of the last ten data check runs were stopped by Excel Online throttling the file. The failure path worked as designed: the problem was caught and the run was flagged as failed instead of passing silently.

Project 4

Demurrage Waiver System

Power AppsSharePointPower AutomatePower Automate Desktop

A request, approval and posting process for charge waivers, built from the request form through to the billing screen.

The problem

When a delay is not the customer's fault, a clerk can waive part of a demurrage charge, but only with approval. Most terminals run this through email chains and re-typing into an old billing screen, which causes errors and delays.

What I built

  • Power Apps request form: pick a container, see the charge worked out live, give a reason and an amount
  • SharePoint lists holding 60 earlier requests and 150 containers
  • Approval flow that sends requests up to NGN 500,000 to the Billing Supervisor and larger ones to the Commercial Manager, records the decision and emails the requester
  • Desktop robot that enters approved waivers into the billing screen, retries when the screen is busy and logs every result
  • Five rules enforced: waiver cannot exceed the claim, one open request per container, approval routing by amount, reference format and one waiver per invoice

What it shows

12 of 16queue rows posted correctly, NGN 4,401,000 in total
4 of 4bad rows stopped with the right error code
0duplicate postings when the robot was run again
5approval and failure tests run

The four rejected rows were deliberate test cases: invoice not found, amount above balance, invalid approval reference and waiver already applied. The robot ran on a laptop in attended mode.
